# Process log

Append-only. Each entry is a decision actually made, dated, with the reasoning. Not a plan, a record.

# Note
Every code/decision written in this project have been previously handled by me in my other silo/build up projects to this, so feel free to check it out for more indepth view on how i handle things. Thanks.

## 2026-11-09

- **Currency stays in top-level `money/`, not nested inside `accounts/`.** Early framing called `accounts/` a "mini bank" with its own currency folder, which contradicted the design doc's own layout (§8). Decided in favor of §8: one currency implementation, `accounts` just depends on `money.Currency`.
- **`money.Currency` uses integer `DecimalPlaces`, not Bank's float `ScalingFactor`.** Direct application of the design doc's principle 3 — floats don't belong in the money path, even for metadata about the money.
- **`accounts/types` flattened into `accounts` directly.** Nothing else was ever going to live in that namespace, so the extra nesting was pure ceremony.
- **Bank's `Deposit`/`Withdraw`/`Transfer` methods, the per-account `sync.Mutex`, `lockInOrder`, the `Bank` aggregator, and `transaction_ledger.go` were not ported.** The write-ahead/replay model means the ledger is the only writer, applying balance changes by replaying the journal. A mutex-guarded `Deposit` method on the account struct itself is a second, competing writer — it doesn't get safer by adding a lock, it gets wrong twice.
- **`BaseAccount` carries an explicit `Kind` enum** (`customer_current`, `customer_savings`, `merchant`, `house`, `suspense`) rather than relying on Go's type system alone to distinguish account kinds. The ledger needs to switch on kind for rules (overdraft only on current, exactly one house/suspense per currency), and that's cheaper to do against a field than a type switch everywhere.
- **`BaseAccount` no longer embeds `Customer`.** Bank's model embedded a customer owner on every account, including ones that structurally can't have one (House, Suspense). Customer ownership is now only embedded on `CurrentAccount`/`SavingsAccount`.
- **`Line` carries `CurrencyCode` and a `Reference` (JobID + CounterpartyAccountID); `Entry.Validate` balances debits against credits per currency, not globally**, with overflow-checked summation. Required by the design doc's §3 — a cross-currency transfer cannot balance as a single pool, so a global balance check would silently accept nonsense.
- **Seed data holds `accounts` + `operations`, never `entries`.** Entries are the ledger's output, produced by replaying an operation through `Post`. Seeding pre-built entries skips the validation path entirely and breaks the design doc's principle 1 — the journal stops being the thing that produced the state.
- **Seeded operations carry no `job_id`.** Job IDs are generated by the system (`jobs/`) at the moment an operation is processed, not supplied ahead of time — seeding one would imply the caller controls idempotency keys, which isn't decided yet (see the design doc's open questions).
- **`internal/journal` is split into `writer.go` (the Post/live path: `LogWriter.Append`) and `recovery.go` (the Open/startup path: `RecoverAndClean`)**, mirroring the two flows in §6 of the design doc as two files, not one undifferentiated package.
- **Added `journal.FileJournal`**, a lazy adapter wrapping `LogWriter`/`RecoverAndClean`: `Recover()` opens/truncates/closes on its own, `Append()` opens the `LogWriter` lazily on first call. One value ends up capable of both operations, in the same order the design doc's §6 Open flow describes (recover, replay, *then* open the writer), without two file handles open at once.
- **`ledger.Journal` interface (`Append`, `Recover`, `Close`) is declared in `ledger`, not `journal`; the compile-time assertion (`var _ Journal = (*journal.FileJournal)(nil)`) lives in `ledger` too.** The interface references `journal.RawEntry`, so `ledger` already depends on `journal` one-way. Asserting from inside `journal` would need `journal` to import `ledger` back — a cycle.
- **All sentinel errors centralized into `internal/errors`, one file per owning package, package name `apperrors` (not `errors`).** Naming it `errors` would shadow the stdlib `errors` package — and `errors.Is`/`errors.As` specifically — in every file that eventually needs both. Note for future additions: the package is a flat namespace regardless of file layout, so names must stay unique across the whole package, not just within one file (`ErrInvalidAmount` collided between what's now `ErrAccountInvalidAmount` and `ErrLineInvalidAmount`).
- **Added `internal/constants` for KYC tiers** (`KYCTier`, `TierLimitsByTier`) ahead of building the actual `can_transfer` check. `Tier` lives on `Customer` and `Merchant`, not on `BaseAccount`/House/Suspense — KYC verifies an identity, not a ledger-internal account. A customer's current and savings accounts share one tier value in seed data because the tier belongs to the person, not the account.
