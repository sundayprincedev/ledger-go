# Process log

Append-only. Each entry is a decision actually made, dated, with the reasoning. Not a plan, a record.

# Note
Every code/decision written in this project have been previously handled by me in my other silo/build up projects to this, so feel free to check it out for more indepth view on how i handle things. Thanks.

## 2026-11-09

- **Currency stays in top-level `money/`, not nested inside `accounts/`.** Early framing called `accounts/` a "mini bank" with its own currency folder, which contradicted the design doc's own layout (§8). Decided in favor of §8: one currency implementation, `accounts` just depends on `money.Currency`.
- **`money.Currency` uses integer `DecimalPlaces`, not Bank's float `ScalingFactor`.** Direct application of the design doc's principle 3 — floats don't belong in the money path, even for metadata about the money.
- **`accounts/types` flattened into `accounts` directly.** Nothing else was ever going to live in that namespace, so the extra nesting was pure ceremony.
- **Bank's `Deposit`/`Withdraw`/`Transfer` methods, the per-account `sync.Mutex`, `lockInOrder`, the `Bank` aggregator, and `transaction_ledger.go` were not ported.** The write-ahead/replay model means the ledger is the only writer, applying balance changes by replaying the journal. A mutex-guarded `Deposit` method on the account struct itself is a second, competing writer — it doesn't get safer by adding a lock, it gets wrong twice.
- **`BaseAccount` carries an explicit `Kind` enum** (`customer_current`, `customer_savings`, `merchant`, `house`, `suspense`) rather than relying on Go's type system alone to distinguish account kinds. The ledger needs to switch on kind for rules (overdraft only on current, exactly one house/suspense per currency), and that's cheaper to do against a field than a type switch everywhere.
- **`BaseAccount` no longer embeds `Customer`.** Bank's model embedded a customer owner on every account, including ones that structurally can't have one (House, Suspense). Customer ownership is now only embedded on `CurrentAccount`/`SavingsAccount`.
- **`Line` carries `CurrencyCode` and a `Reference` (JobID + CounterpartyAccountID); `Entry.Validate` balances debits against credits per currency, not globally**, with overflow-checked summation. Required by the design doc's §3 — a cross-currency transfer cannot balance as a single pool, so a global balance check would silently accept nonsense.
- **Seed data holds `accounts` + `operations`, never `entries`.** Entries are the ledger's output, produced by replaying an operation through `Post`. Seeding pre-built entries skips the validation path entirely and breaks the design doc's principle 1 — the journal stops being the thing that produced the state.
- **Seeded operations carry no `job_id`.** Job IDs are generated by the system (`jobs/`) at the moment an operation is processed, not supplied ahead of time — seeding one would imply the caller controls idempotency keys, which isn't decided yet (see the design doc's open questions).
- **`internal/journal` is split into `writer.go` (the Post/live path: `LogWriter.Append`) and `recovery.go` (the Open/startup path: `RecoverAndClean`)**, mirroring the two flows in §6 of the design doc as two files, not one undifferentiated package.
- **Added `journal.FileJournal`**, a lazy adapter wrapping `LogWriter`/`RecoverAndClean`: `Recover()` opens/truncates/closes on its own, `Append()` opens the `LogWriter` lazily on first call. One value ends up capable of both operations, in the same order the design doc's §6 Open flow describes (recover, replay, *then* open the writer), without two file handles open at once.
- **`ledger.Journal` interface (`Append`, `Recover`, `Close`) is declared in `ledger`, not `journal`; the compile-time assertion (`var _ Journal = (*journal.FileJournal)(nil)`) lives in `ledger` too.** The interface references `journal.RawEntry`, so `ledger` already depends on `journal` one-way. Asserting from inside `journal` would need `journal` to import `ledger` back — a cycle.
- **All sentinel errors centralized into `internal/errors`, one file per owning package, package name `apperrors` (not `errors`).** Naming it `errors` would shadow the stdlib `errors` package — and `errors.Is`/`errors.As` specifically — in every file that eventually needs both. Note for future additions: the package is a flat namespace regardless of file layout, so names must stay unique across the whole package, not just within one file (`ErrInvalidAmount` collided between what's now `ErrAccountInvalidAmount` and `ErrLineInvalidAmount`).
- **Added `internal/constants` for KYC tiers** (`KYCTier`, `TierLimitsByTier`) ahead of building the actual `can_transfer` check. `Tier` lives on `Customer` and `Merchant`, not on `BaseAccount`/House/Suspense — KYC verifies an identity, not a ledger-internal account. A customer's current and savings accounts share one tier value in seed data because the tier belongs to the person, not the account.

## 2026-11-10

- **`IDRegistry` rebuilt on a `sync.Mutex` + `map[string]JobState` instead of `sync.Map`.** `sync.Map` only gives atomic check-then-set via `CompareAndSwap` on a single key; `Complete`/`Release` need to check state and then decide what happens next (reject if not in-flight, delete if found) as one step. A plain mutex makes read-check-write per job ID a single critical section instead of working around `sync.Map`'s API.
- **`Register` no longer seeds `StatePending`.** Looking up an unseen ID now stores it as `StateInFlight` directly — registering a job *is* starting work on it, not queueing it. An existing ID is returned as-is with `New: false`; nothing gets overwritten.

  Flagging, not fixing: `StatePending` is still declared (`id.go`) but nothing in `id.go` writes it anymore, and `Complete`'s rejection path builds a `JobNotPendingError` (message: "want pending") while actually comparing against `StateInFlight`. If `StatePending` is meant to be set by a different caller before the ledger ever sees the job (the worker enqueues as pending, the ledger flips it to in-flight on `Register`), that's consistent — but as it stands the error text and the check it comes from don't agree. Worth confirming the intent before `jobs/` starts depending on either state.
- **Added `SeedCompleted(id) (duplicate bool)`, separate from `Register`.** This is the replay-time path from the design doc's §6 Open flow ("skip and log duplicate IDs") — marks a job ID recovered from the journal as completed without going through the live `Register`/`Complete` state machine, and reports whether it was already present so replay can log the duplicate instead of silently reapplying it.
- **`var _ Journal = (*journal.FileJournal)(nil)` commented out in `ledger/journal.go`**, with a note to move it to `main` later. Keeping that satisfaction check inside the `ledger` package ties the interface to one concrete implementation inside the library itself; moving it to the composition root (`cmd/ledger`) means `ledger` only ever talks about the interface, and "does the file journal actually satisfy it" gets checked where the two are actually wired together.
- **`Complete` rejects with `JobNotInFlightError` (message "want in_flight"), replacing `JobNotPendingError`.** The old type said "want pending" while the check compared against `StateInFlight`, which was the mismatch flagged above. A registered job is in flight, not pending.
- **`Entry.Validate` wraps every failure in `EntryValidationError{Step, LineIndex, Err}`, with the detail moved into typed errors (`CurrencyError`, `DirectionError`, `BalanceError`, `EntryDecodeError`) that unwrap to their sentinels.** A caller finds out which step failed with `errors.As` and can still match the sentinel with `errors.Is`. `LineIndex` is `-1` for entry-level failures. The inline `fmt.Errorf` calls that used to carry that detail are gone from `ledger`.
- **The journal got the same treatment: `WritePipelineError{Step}` for `LogWriter` and `RecoveryPipelineError{Step, Offset}` for `RecoverAndClean`.** The three corruption checks (header CRC, payload size, payload CRC) are distinct steps instead of one shared message, and the first `os.OpenFile` in recovery, which used to return a bare `err`, is now wrapped. `Offset` is `-1` when the failure isn't tied to a record.

- **`strings.Builder` for flat messages, `fmt.Sprintf` for templated or branching ones.** Applied to the accounts errors, `CurrencyError`/`DirectionError`/`BalanceError`/`EntryDecodeError`, and `GenerateSummary`. `EntryValidationError`, `WritePipelineError` and `RecoveryPipelineError` stay on `Sprintf`. ## 2026-11-12

- **Ported only the generic half of jobWorker into `internal/jobs`:** `Job`, `JobState`, `Transition`, `WorkerPool` with panic isolation, and the error types. Left behind: everything payment-specific (`PaymentPayload`, `doWork`, `ProcessorError`) and `JobRegistry`/`resolver`/`Dispatch`. `IDRegistry` already covers ledger-commit idempotency, and worker-level stale detection waits until `Post` exists to call into.
- **Channels are created in `main` and injected; the pool never creates or closes one.** Context works the same way: the pool derives a child context from an injected parent and never originates one. Only the creator of a channel closes it, and `Start` takes `jobCh`, `errCh` and `resultsCh` as parameters.
- **Errors stay plain `error` returns everywhere except the goroutine seam**, where `runJob` turns them into sends on the injected `chan error`. Every error type is self-describing (job ID, step, offset), so one shared channel doesn't lose where an error came from.
- **`jobs.JobState` and `ledger.JobState` stay separate types because they answer different questions:** execution lifecycle versus ledger commit state. How they line up: `running` ↔ registry `in_flight` (claimed at `Register`); `committed` ↔ journal append and sync done while the registry is still `in_flight` (the crash window); `completed` ↔ registry `completed`; `failed`/`canceled` before commit ↔ registry entry released.
- **`Transition` rejects any move out of a terminal state.** The ordinal comparison alone allowed `Completed → Failed` and `Failed → Canceled`, because the terminal states have increasing ordinals.
- **Naming constraints in `apperrors`:** the worker-runtime error is `WorkerJobError` because `JobError` was already taken by the registry errors, and `TransitionError` carries `From`/`To` as strings because `apperrors` can't import `jobs` without a cycle.

## 2026-11-13

- **Stages run sequentially inside one `WorkFunc`, not as channel-chained goroutines.** Nothing in the pipeline is I/O-bound yet (KYC is an in-memory lookup, validation and splitting are arithmetic), so chained stages would add a second concurrency model next to `WorkerPool` for no gain. Revisit when a stage becomes a network call: fan that stage out and keep append as the single serialized stage.
- **`Intent` mirrors the seed operation shape; `OpType` is `single_transfer`, `bulk_transfer` or `house_transfer`.** `OpType` is the dispatch key for later stages (split or not, KYC or not). Known gap: the type exists, but nothing rejects an unknown value yet.
- **Job IDs are a CRC32 of the value-moving fields (`Note` excluded), as hex, generated once in `NewWriteJob` and passed into the pipeline.** Same "no UUIDs, derive from content" call as jobWorker, so a retried intent collides with itself on purpose. Known limitation: 32 bits means two different intents can share an ID (about 1% at 10k distinct intents, about 50% near 77k), and the pipeline would then treat the second as a duplicate. Worth revisiting before real volume.
- **`Register` is the duplicate check, with no separate `LoadJob`.** `New: true` continues; `completed` returns `ErrJobAlreadyCompleted` (TODO: return the original result); `in_flight` returns `ErrJobAlreadyInFlight`, because a second caller continuing would post the same transfer twice.
- **`JobPipelineError{JobID, Step, Err}` is the job-level step error; the journal keeps its own `WritePipelineError`.** Same word, different layer, and one enum would mix file-op steps with job steps. Journal errors nest inside job-step errors later. Steps so far: `register`, `complete`. `checkContext` guards each stage boundary.
- **`StartWritePipeline` isn't a `WorkFunc`; `WriteWorker.WriteWork(registry)` binds it to one, and `NewWriteJob(intent, timeout)` builds the `*Job`.** A wrong payload type returns `ErrInvalidPayload` as a job failure instead of panicking.
- **`Job.timeout()` falls back to `DefaultJobTimeout` (5s) when the field is zero.** `WithTimeout(ctx, 0)` yields an already-expired context, so every job built without a timeout failed. The 5s value is a placeholder with no load data behind it.
- **`runJob` is the only place panics are recovered.** The pipeline's own `recover` was removed because it ran first and turned panics into ordinary errors, losing the "panic" label and stack. `runJob`'s panic path now also moves the job to `Failed` and emits a failed `JobResult`; before, it only wrote to `errCh`, which left the job `Running` with no result.
- **Registry lifecycle inside the pipeline is one flag, `claimed`.** It is set when `Register` returns a fresh entry and cleared after `Complete`; a deferred `Release` runs if it is still set, which covers error returns and panics alike. Only the creator of an entry ever releases it, so a duplicate can't delete another job's entry. Rule still to enforce: once the journal append succeeds, the entry must not be released.
- **Removed dead code:** `ledger.StatePending` (nothing wrote it after the 11-10 rewrite) and `ErrJobConcurrentStateChange` (left over from the `sync.Map` version).

## 2026-11-14

- **Job IDs are now the full SHA-256 of the value-moving fields, hex-encoded (64 chars), replacing the CRC32.** This resolves the collision limit recorded on 11-13: with 32 bits, two different intents could share an ID and the second would be rejected as a duplicate. `Note` is still excluded.
- **`Intent.Validate()` is the first stage of the write pipeline, ahead of the context check and `Register`.** A rejected intent never claims an ID, so there's nothing to release. It returns `IntentValidationError{Step, RecipientIndex, Err}`, the same shape as `EntryValidationError` (`RecipientIndex` is `-1` when the failure isn't tied to a recipient), and the pipeline wraps it as a `JobPipelineError` at step `intent`. `main` can also call `Validate()` itself to reject a bad intent before building a job.
- **Rules per `OpType`:** every type needs a known `OpType`, a positive amount, and a known currency. `single_transfer` and `house_transfer` need distinct from/to accounts. `bulk_transfer` needs a sender, at least one recipient, and each recipient needs an account that isn't the sender and a positive weight. A zero-weight recipient is rejected because it would produce a zero-amount entry line, which `Entry.Validate` rejects anyway.
- **Not validated yet, on purpose:** that bulk weights sum to the whole (the constant belongs to `Allocate`, which isn't ported, so it will own that check), and that a `house_transfer` has a house account on one side (that needs the account store to look kinds up). Until then `house_transfer` is validated as a plain from/to pair.

## 2026-11-16

- **`ledger.AccountStore` is the lookup the KYC stage needs: account ID to `AccountProfile{ID, Kind, CurrencyCode, Tier}`.** It lives in `ledger` next to `IDRegistry`, since the design doc puts balances and the ID map there. `Lookup` returns `AccountError` wrapping `ErrAccountNotFound`, so an unknown account in an intent fails at the stage that reads it.
- **The store holds profiles only, not the account structs.** Nothing reads balances yet, and the apply stage hasn't decided how balances get mutated safely. The typed `Add*` methods already have the account in hand, so adding the pointer then is a small change.
- **There is one typed `Add*` method per account type (`AddCurrent`, `AddSavings`, `AddMerchant`, `AddHouse`, `AddSuspense`), and the store sets `Kind` from the method called.** This keeps tier coming from the right place (`Customer.Tier`, `Merchant.Tier`) and means a house or suspense account can never be given a tier. It also means a wrongly set `Kind` field on the account can't make the store disagree with itself.
- **Duplicate and empty IDs are rejected on `Add`** (`ErrAccountExists`, `ErrAccountIDRequired`). Accounts arrive from seed JSON, which is an outside boundary, and a silently overwritten or empty-keyed account would be hard to trace later. The map sits behind an `RWMutex`, since workers read it concurrently.
- **Deferred on purpose:** how tier limits relate to currency (the numbers are plain minor units today, and you're leaning toward a single number for now).
- **The daily transfer limit is removed from `TierLimits`, leaving only `SingleTransferLimit` and `SingleReceiveLimit`.** Enforcing it would mean tracking how much each account has moved that day, which is extra state and work on every transfer for a check the project doesn't need yet. I also fixed the `SingleReceiveLlimit` typo while editing the file.
- **KYC is one per-account check, applied in order: the sender first, then the receiver by op type (`single_transfer`/`house_transfer` check the to account, `bulk_transfer` checks every recipient after the split).** An account with no limits for its tier fails with `TierLimitsError` at step `kyc`, wrapping `ErrTierLimitsNotFound`.
- **`kycChecker(store, intent)` returns plain errors, and the pipeline wraps them once as `JobPipelineError{Step: kyc}`.** The per-account helper, `checkAccountLimit`, does lookup, then kind, then tier, then limits, then the amount. Failures are `AccountError` (unknown account), `TierLimitsError` (no limits for the tier), and `LimitError{AccountID, Amount, Limit}` wrapping `ErrTransferLimitExceeded` or `ErrReceiveLimitExceeded`. An amount exactly at the limit passes.
- **House and suspense accounts skip KYC entirely.** They carry no tier, and without the skip a `house_transfer` from a house account would fail with "no limits for tier 0".
- **Bulk transfers check only the sender for now.** A recipient's receive limit applies to its share of the split, and the shares don't exist until `Allocate` is ported. Checking recipients against the full total would reject legitimate transfers. A TODO in `kycChecker` marks where the per-recipient check goes.
- **A failure after `Register` is now tested, and the claim is released.** KYC is the first stage that can fail after registering, so the release-on-failure path finally has a test: a KYC rejection leaves no registry entry behind.
- **`Allocate` is ported into `money/allocate.go`, where the design doc puts allocation.** It's the largest-remainder split from trainingCenter: shares are floor(weight × amount ÷ 1000), and the leftover units go one each to the largest remainders, ties going to the lowest index. The weights are parts of `FullWeightUnits` (1000), exported so whoever builds a bulk intent shares the contract. The trainingCenter copy is untouched.
- **Changes from the trainingCenter version.** Each failure has its own error in `errors/money.go`; before, a bad amount reported the weights error. The multiply is overflow-checked. Weights outside 0 to 1000 are rejected up front; the old unchecked sum could wrap around to exactly 1000 with absurd weights (two `MaxInt64`s and a 1002 summed to 1000) and produce garbage shares. Remainders live in a slice instead of a map, with the same ordering.
- **A share can be zero.** A small weight on a small amount rounds to nothing (amount 1 across five equal weights gives `[1,0,0,0,0]`). Intent validation rejects zero weights, but that doesn't prevent zero shares, so the entry builder has to skip them: `Entry.Validate` rejects a zero-amount line.
- **The house cut of a transfer is a weight out of `money.FullWeightUnits` (1000), held in `constants.HouseFeeWeight`.** Using the same scale as `Allocate` means the split can be one `Allocate` call with weights `{house, 1000 - house}`, which guarantees the two shares add up to the amount. Floats stay out of it. The current value, 20 (2.0%), is a placeholder; jobWorker used 20%.
- **`money.SplitHouseCut(amount, houseWeight)` returns `[house, receiver]`, indexed by `HouseShareIndex` and `ReceiverShareIndex`.** The weight is a parameter, not read from the constant inside, so the same function can apply the cut per share in a bulk transfer later. The body is a skeleton for now.
- **A direct transfer is posted through suspense in three legs:** sender to suspense for the full amount, suspense to house for its cut, suspense to the receiver for the rest. Suspense nets to zero, which is what the design doc's "holds money in flight" means.
- **A direct transfer is one `Entry` with six lines, not three entries.** Each journal append is atomic, but three appends can crash between them and leave the sender debited with the money stuck in suspense. The entry ID is the job ID, and replay skips duplicate IDs, so three entries sharing one job ID would have the second and third dropped on recovery. One entry is one atomic write with one ID, and it still balances per currency.
- **The house only takes a cut when the amount is strictly above `constants.HouseFeeThreshold` (10000 minor units).** At or below it the house share is 0. This avoids a zero-amount house line on small transfers. With a cut applied, the house share is never zero at the current weight, but without one the entry has four lines and no house legs, so the builder still omits the house leg when the share is 0. The threshold, like the KYC limits, is a plain number in minor units with no currency attached, deliberately kept simple for now.
- **`AccountStore.FindByKind(kind, currency)` finds the house and suspense account for a currency, and only those.** The design doc says house is per currency and suspense is one per currency, so `AddHouse` and `AddSuspense` now enforce that: a second one in the same currency is rejected with `ErrSystemAccountExists`, and the rejected account isn't stored. That makes the lookup a map hit instead of a scan on every transfer. Customer kinds can't be found this way because many exist per currency; asking for one returns `ErrNoAccountForKind`.
- **`SplitHouseCut` now takes only the amount and reads the fee constants itself.** This changes the earlier `(amount, houseWeight)` signature: the threshold rule and the fee both live inside it, so the pipeline just calls it and gets `[house, receiver]`. The pipeline debits the sender to suspense by the sum of the two shares.
- **`SplitHouseCut` fails on a non-positive amount (`ErrSplitInvalidAmount`) and on overflow of `amount × HouseFeeWeight` (`ErrSplitOverflow`), and checks its own output.** `verifySplit` rejects any result where the shares are negative or don't add up to the amount, with `SplitMismatchError{Amount, House, Receiver}` wrapping `ErrSplitMismatch`. Because the function guarantees the shares sum to the amount, the debit to suspense always equals `intent.Amount`, and a bug in the split can't silently move a different amount of money.
- **Correction: `HouseFeeWeight = 20` currently means 20%, not 2%.** `SplitHouseCut` computes `amount × HouseFeeWeight ÷ 100`, so the constant is a percent and the earlier per-mille framing (and the "2.0%" in the bullets above) no longer applies. Getting 2% means dividing by 1000 or changing the value. The constant's name and number are still placeholders.
- **`SplitHouseCut` computes the cut directly instead of calling `Allocate`, and rounds in the receiver's favour.** The house share is the floor of the percentage and the receiver takes the remainder, so the two always add up to the amount and the sender is debited exactly `intent.Amount`. This is the one place a split doesn't use largest-remainder allocation. For two shares it differs from `Allocate` by at most one unit.
## 2026-11-17

- **Update: `SplitHouseCut` now divides by 1000, so `HouseFeeWeight = 20` is 2.0%, as originally defined.** This supersedes the "currently means 20%" correction above. The constant is still a placeholder value.
- **The currency check lives in the account store: `AccountStore.CheckCurrency(accountID, currencyCode)`.** The store owns account facts, such as which currency an account holds, and the pipeline owns policy, which is what to do when they differ. A mismatch returns `CurrencyMismatchError{AccountID, AccountCurrency, AmountCurrency}` wrapping `ErrCurrencyMismatch`, so a later conversion stage can branch on it with `errors.As` and already knows both currencies. Until conversion exists, a mismatch fails the job at step `currency`.
- **The currency check is meant to run before KYC.** The KYC limits are plain numbers with no currency attached, so the amount has to be known to be in the right currency before it is compared to them. It is not wired into the pipeline yet.
- **A failure in `SplitHouseCut` fails the job at step `split`.** After KYC, the amount is within the sender's limits, so the split's own errors shouldn't be reachable through the pipeline. The step exists so that if one ever does fire, it is attributed to the split.
- **The pipeline branches on op type right after the claim: bulk transfers take their own path, and direct transfers run currency check, KYC, then split.** The checks differ per type: a bulk transfer checks every recipient, and only against its share after `Allocate`. So running the direct checks above the branch would apply the wrong ones to bulk intents. The bulk path is a TODO for now. The direct path is the `else`, so a bulk intent can't fall into it.
- **The currency checks validate the sender against the intent's currency first, then the receiver against the same code.** Once the sender passes, the intent's currency equals the sender's, so the receiver check is receiver against sender. Checking the two accounts only against each other would let an intent that names a currency neither account holds move the wrong currency. A sender mismatch is a malformed request, a receiver mismatch is the future conversion trigger, and `AccountID` on `CurrencyMismatchError` says which side failed. The receiver check is not wired yet.
- **Correction to the branch above: there is no `else`.** Bulk gets its own block, which you'll write fresh. Anything that isn't `single_transfer` after that block fails at a new step, `dispatch`, with `UnsupportedOpTypeError` wrapping `ErrOpTypeNotSupported`, and then the direct-transfer stages run as normal flat code. The effect is that nothing unfinished can slip through as a success: a bulk intent that falls out of its empty block, and a `house_transfer`, which has no path yet, both stop at `dispatch`, and the deferred release frees the claim. Each op type gets a path by adding its own block and removing it from this guard.
- **The receiver's currency is now checked against the intent's currency**, right after the sender's, as `currCheckErrorReceiver`. Both fail at step `currency`, and the `AccountID` inside `CurrencyMismatchError` says which side. A receiver mismatch is where conversion will attach later.
- **Known gap: the pipeline still builds no entry.** The direct path splits the amount and then goes straight to `Complete`, so a job that passes reports success without posting. The next stages are line building, entry validation, marshal, append and apply.
- **The pipeline checks that `SplitHouseCut` returned exactly two shares before indexing them.** The line builder reads `splitCut[0]` (house) and `splitCut[1]` (receiver) directly, and a short slice would panic. The guard fails the job at step `split` with `ErrSplitShareCount`. `SplitHouseCut` already guarantees two shares, so this protects the direct indexing, not the split.
- **Line building has its own step, `build_entry`, and starts with the context check.** A cancelled context stops the job before any lines are built. The suspense account for the currency comes from `FindByKind(KindSuspense, intent.CurrencyCode)`, and a missing one fails at `build_entry` with `KindError` wrapping `ErrNoAccountForKind`.
- **The suspense account in the pipeline is a pointer to a struct built from the store's profile, and it is not the stored account.** The store holds profiles only (ID, kind, currency, tier), so this is a new `Suspense` with a zero balance. It is fine for building lines, which only read the ID and currency. It must not be used to apply balances. Applying needs the store to hand out the real account, which waits on deciding how balances are mutated safely across workers.
- **At this stage everything the pipeline builds is a record, not memory.** Suspense (and house) lines are just entry lines naming an account; nothing is stored or changed in memory yet. The first real in-memory balance work is the apply stage, and it will cover house and suspense as well as the users, because the startup trial balance needs every account in a currency to sum to zero.
- **A direct transfer is written as lines of legs, and the suspense ID sits on the second line.** "Sender to suspense" is two lines: the sender is debited with the suspense ID as the counterparty, and suspense is credited with the sender as the counterparty. The reference always names the other side of the leg, which is how suspense tracks whose money it holds, since the account itself doesn't say.
- **The house account is looked up only when the house share is above zero.** At or below the threshold there is no house leg, so a currency with no house account doesn't break small transfers. A missing house account when a cut applies fails at `build_entry` with `KindError` wrapping `ErrNoAccountForKind`, and the claim is released.
- **The direct transfer's lines are appended in the order they're written, into a slice with capacity 6.** The order is: sender debit, suspense credit, then (only when a cut applies) house credit and suspense debit, then receiver credit and suspense debit. The first version wrote to fixed positions in a length-6 slice. That overwrote the house lines with the receiver's, and it left empty lines at the end, which `Entry.Validate` rejected. `append` keeps the same order without tracking indexes, and the entry is 4 or 6 lines on its own.
- **The receiver's two lines use the receiver's share (`splitCut[1]`), not the total debit.** Using the total would still balance, so `Entry.Validate` wouldn't catch it, but the receiver would get the full amount and suspense would end negative by the house cut. A balanced entry is not necessarily a correct one, so the net effect of each leg needs its own test.
- **A failed `Entry.Validate` fails the job at step `validate_entry`**, wrapping the `EntryValidationError`, and the claim is released.
- **The direct transfer's line building moved out of the pipeline into `buildDirectEntry(store, jobID, intent, splitCut)`.** The code is the same; it only moved. The entry was local to the pipeline, so nothing could inspect the lines. As a function it can be given inputs and checked: the tests assert the exact six lines in order (and the four without a cut), plus the net effect per account credit-normal. The sender loses exactly the amount, the house gains its share, the receiver gains its share, and suspense ends at zero. Putting the receiver's amount back to the total makes the test fail with `want 58800, got 60000`.
- **After validation the pipeline checks the context again before marshalling, at step `marshal`.** It's the last cheap point to stop before the entry is turned into a payload and handed to the journal.
- **`Entry.Marshal` wraps its failure as `EntryEncodeError`**, the mirror of `EntryDecodeError`. The payload is the JSON of `{id, lines}`; the timestamp is not part of it, because it comes from the journal header at append. A test shows a marshalled entry decodes back to the same ID and lines and is validated again on the way in, which is what recovery will rely on.
## 2026-11-18

- **The pipeline appends to the journal at step `append`, and a failed append returns the journal's own error nested inside it.** The context is checked once more right before the append. - **Known limit:** if `Recover()` fails after `Reset()`, the writer is no longer poisoned, and nothing stops the next job from appending after a torn tail. The interface has no way to poison it again.

- **The write pipeline poisons the journal when `Recover()` fails after `Reset()`.** The next job's append is then refused as poisoned, which is classified as recovery-required, so that job resets and tries recovery again. ## 2026-11-26

- **A resolver failure returns an error and never poisons the journal.** The resolver reads the journal and updates the registry and balances. It does not write the file, so if it fails, the source of truth is as clean as `Recover()` left it. Poisoning would shut down a healthy journal over a registry problem. The failure is reported in `AppendFailureError.ResolverErr`.
- **Every job runs the resolver first, when something is pending.** In the write pipeline, after intent validation and before `register`, `PendingIDs()` is checked. If it is not empty, the resolver runs. With nothing pending it costs one registry lookup and never reads the journal. This is how a stuck pending job gets settled without waiting for another append failure. A retry of the pending job itself benefits too: it is settled first, so `register` then sees it completed, and the retry is re-acked, or sees it freed, and the retry writes fresh.
- **If the resolver fails at the start of a job, that job fails at the new step `resolve` and appends nothing.** Refusing writes while the ledger is unsettled is the safer choice, because a resolver failure means a corrupt or unreadable record or a balance overflow, which is serious. The cost is that every job fails until the cause is fixed. The writer is not touched.
- **The append-failure recovery block is context-guarded in two places, and deliberately not in two others.** The context is checked before `Reset()` and before the resolver, using `checkResolveContext`, so a cancelled or timed-out job doesn't start recovery. The reset-then-recover pair has no check between its two calls, because a reset followed by a skipped recover would open a fresh writer after a torn tail. `MarkPending` also has no check: the claim was already given up, and skipping it would leave the job `in_flight` forever. When a guard trips, the append failure carries a `context`-step `ResolverErr`. Nothing is lost by skipping. Every failure that requires recovery has already poisoned the writer, so the next job's append is refused, which sets recovery-required and runs the whole sequence again. Any leftover pending job is settled at the start of that job.
- **Currency conversion is not built yet; the receiver-currency mismatch still rejects the job at step `currency`.** Seeding an NGN to USD transfer showed this. Conversion works on minor units, whose scale differs per currency (USD has 2 decimals, JPY has 0), so the raw amount can't be multiplied by a rate. It must be converted with the decimal places of both sides and a rounding rule, in integer math, not with the float helpers in `money/currency.go`, which are for the display edge.
- **Exchange rates are a fixed table in `constants/fx.go`, expressed against USD, in integers.** `FXPerBase[code]` is how many micro-units of that currency one USD buys, with `FXRateScale` of 1,000,000 as one unit, so USD is 1,000,000 and NGN is 1,500,000,000. A rate between two currencies is derived through USD, which keeps the table to one entry per currency and means the rates can never disagree with each other, as a table of every pair could. The values are placeholders, not market data. A test checks that every known currency has a positive rate and every rate has a currency.
- **Next, in order:** an integer converter in `money/` that takes source and target currencies and a minor-unit amount and applies the rounding rule, then the FX position accounts that let a cross-currency entry balance per currency, then the pipeline branch. Decided defaults, still to confirm: the house cut is taken in the source currency first, and the remainder is converted, rounded half up.
- **`money.UnitConverter(fromCode, toCode, amount)` converts minor units in exact integer math.** It computes `amount × rateTo × 10^toDecimals ÷ (rateFrom × 10^fromDecimals)` as one fraction in `math/big` and divides once at the end, rounding half up. The first version multiplied by the rate scale twice in int64, which overflowed above about 9.2 million minor units, and it divided twice, truncating each time. Doing the arithmetic in big integers removes the overflow, and the single division means rounding happens exactly once. The decimal places of both currencies are part of the fraction, so USD to JPY drops two decimals and JPY to USD adds them. A result that doesn't fit in int64 returns `ErrConvertOverflow`, a negative amount returns `ErrConvertInvalidAmount`, and an unknown code returns `CurrencyError`, which names the bad code. The same currency returns the amount unchanged. `NormalizeAmountByFloor` is not used: it takes a float in major units, and floor is not the confirmed rounding rule.
